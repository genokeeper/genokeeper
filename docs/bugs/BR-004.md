- **Found:** 2026-11-02
- **Where:** `src/genokeeper/deletions/screen.py` (`screen`, `is_common`, `rare`) against
  `src/genokeeper/calibrate/build.py` (`build_deletions`' size cut, `judge_library`'s
  `rare`); `src/genokeeper/cnv/screen.py` calls `is_common` as well.

The run screens each deletion through `screen`, whose `COMMON` test is `is_common` over the
whole list of gnomAD-SV records. The calibration measures the same screen through a second
path: `build_deletions` repeats the `SHORT` cut by hand (`d.length >= t.min_length`) and
`judge_library` calls `rare`, an indexed copy of `is_common`. Two implementations of one
test can drift apart, and a drift would make the table measure calls the run never shows.
`tests/test_deletion_screen.py::test_rare_agrees_with_is_common_over_the_whole_list` exists
only to prove that today they agree.

**Evidence.** By reading at f81626d. The table plumbing half of the same concern (the
write, read and open functions copied from slice 3a) is already one module,
`calibrate/classes.py`, writing through `calibrate/tables.py`.

**Suggested fix (a hypothesis):** one population index on `Screen` that `screen`,
`population_match`, `rare` and the depth screen all go through, and the calibration's size
cut through the screen's own test. Must not change: the screen's output, the table's format
and any step key. Alternative: leave it, as no output differs today.

**What this evidence does not establish:** any present wrong output; the cost is drift.

## Fix

One path. `Screen` indexes its gnomAD-SV records once (`_population`); `population_match`
reads only the records overlapping the call (an insertion's, those within `max_distance`),
in the list's own order, so a tie in AF picks the record the whole list would,
and `is_common(d, s)` and `rare(deletions, s)` are that match against `max_gnomad_af`, so
the run's `screen`, the calibration's `judge_library` and the depth screen's two `COMMON`
tests are one function. `is_short` is the `SHORT` test, which `screen` and the deletion
calibration's size cuts (`build_deletions`, the depth table's 3b deletions) call. Covered by
`tests/test_deletion_screen.py` (`test_population_index_finds_every_overlapping_record`,
`test_population_index_matches_the_whole_list`, which compares the index with the whole
list over random deletions, duplications and insertions, ties in AF included,
`test_common_dropped_and_rare_shown`, `test_insertion_lower_bound_by_position`) and
`tests/test_calibrate_deletions.py` (`test_insertion_common_by_window`, and
`test_calibration_judges_what_the_run_does_not_drop_as_common`, which drives
`judge_library` and the run's `screen` over one `Screen` and fails if `judge_library`
skips the common test);
`test_rare_agrees_with_is_common_over_the_whole_list` is gone with the second path.

Not changed: the screen's output, the table format, any step key or table version. The
truth's own size floors (Truvari's `--sizemin`, the insertion truth's `min_length`) stay
separate, as they cut the truth, not calls. Nor the insertion calibration's own cut
(`build_insertions`, `d.length >= min_length`), which differs from `is_short` for an
INSurVeyor insertion of unknown length (no `SVLEN`, no assembled part): the run shows one,
the calibration never measures it. Moving that cut changes what Truvari is handed (`SVLEN`
1), which is slice 3d's to settle with its calibration.
