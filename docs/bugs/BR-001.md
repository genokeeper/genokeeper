- **Found:** 2026-11-02
- **Where:** `src/genokeeper/deletions/exons.py`, `targets`.

`targets` merges the overlapping exons of a gene's MANE Select and MANE Plus Clinical
transcripts into one target and unions their exon numbers. Where the two transcripts number
the same exon differently, a deletion over that one exon carries two numbers in its claim's
`exons`, for example `[30, 31]`, and the `genome-ask` skill reads them as two exons. The
numbers are labels: the screen's overlap and placement do not read them.

**Evidence.** The packaged `resources/deletions/exons.GRCh38.tsv` (MANE v1.5) has nine genes
with two transcripts (ABCC8, DYNC2H1, LMNA, MUTYH, MYH11, NEB, PCDH15, SCN5A, TRDN). On
`origin/main` at f81626d, `targets(load_exons(), 20)` gives (a script counting the targets
whose `exons` hold more than one number, run against that tree):

```
DYNC2H1 26 of 90 targets carry two numbers
MYH11 36 of 43 targets carry two numbers
```

The other seven number alike. `tests/test_deletion_exons.py::
test_packaged_two_transcript_genes_read_one_number_per_exon` fails there on `DYNC2H1`.

**Suggested fix (a hypothesis):** number a target by its MANE Select exons, and by the Plus
Clinical ones only where it holds no Select exon; the resource marks each row's tag, so
`read_resource` can carry it. Must not change: the bases a target covers, so the screen and
the calibration stay the same. Alternative: keep both numberings, each labelled by its
transcript, which changes `Target.exons`' type for every reader (3d's depth screen, the
spike-ins).

**What this evidence does not establish:** whether a reader would rather see the Plus
Clinical numbering, which some clinical reports use for these genes; and an exon only the Plus
Clinical transcript has (seven across MUTYH, NEB, SCN5A, PCDH15, DYNC2H1 and MYH11) keeps a
number another exon of the Select transcript may also carry.

## Fix

`targets` numbers each target by its MANE Select exons, and by the Plus Clinical ones only
where it holds none; `Exon` carries `select`, which `read_resource` reads from the
resource's tag column. The packaged DYNC2H1 and MYH11 now read one number per target
(the same script on this branch: `DYNC2H1 0 of 90`, `MYH11 0 of 43`). The `genome-ask` skill
says which numbering `claim.exons` uses. Covered by `tests/test_deletion_exons.py`
(`test_targets_number_by_mane_select`, `test_read_resource_marks_plus_clinical`,
`test_packaged_two_transcript_genes_read_one_number_per_exon`).

After the final review: an exon only the Plus Clinical transcript has (seven targets, six
of whose numbers Select gives another exon: DYNC2H1 64, MUTYH 1, MYH11 6, NEB 143, PCDH15
33, SCN5A 6) is now named apart. `Target.plus_clinical` marks a target numbered by that
transcript; `claim.exons` holds Select's numbers alone, and the new
`claim.plus_clinical_exons` the Plus Clinical ones, so a deletion over DYNC2H1's
Plus-Clinical-only exon 64 and Select's exon 64 reads `exons [64]`,
`plus_clinical_exons [64]`, no longer one exon. 3d's depth losses carry the same. Covered by
`tests/test_deletion_exons.py::test_plus_clinical_only_target_marked`,
`tests/test_deletion_screen.py::test_plus_clinical_only_exon_named_apart` (on the packaged
DYNC2H1), `tests/test_deletion_source.py::test_claim_names_plus_clinical_exons_apart` and
`tests/test_cnv_screen.py::test_depth_loss_names_plus_clinical_exons_apart`.

Not changed: the bases a target covers, the resource file (its sha256, which the calibration
tables' versions hold), and the type of `Target.exons`. The new numbers do reach two
calibration-side labels: the depth screen's not-covered exon list, and a spike-in's label
(`calibrate/spikein.py`), which is part of what the spiked CRAM's step key hashes; a spike
in DYNC2H1 or MYH11 would run that step again. No such calibration has run yet. Those two
labels keep a Plus-Clinical-only target's number without the transcript.
