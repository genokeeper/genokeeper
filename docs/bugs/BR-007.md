- **Found:** 2026-10-28 (slice 3a's final review), carried over from the private archive's
  ledger on 2026-11-02.
- **Where:** `src/genokeeper/calibrate/stage3.py`, `stage3_versions`.

As filed, a stage-3 table recorded the five images, the catalog's sha256, Parascopy's md5s and
the FASTA's sha256, but not the `[repeat_loci]` thresholds `measure` withholds a locus by
(`normal_max` through `graded_normal`). After a threshold edit without a new
`genokeeper calibrate --only stage3`, the old table would still open, so a locus HG002 would
now fail would be graded rather than withheld. The entry also noted that the HG002
alignment's tool versions (bwa) are not recorded, and suggested the `[smn]` and `[yleaf]`
grading values join the versions.

**Evidence.** By reading at the time; not run.

**Suggested fix (a hypothesis):** a digest of the loci thresholds in `stage3_versions`, so
`open_stage3` refuses a table measured under other thresholds. Must not change: a table
measured under the same config opens.

**What this evidence does not establish:** whether any threshold edit was planned before the
next stage-3 calibration.

## Fix

Does not reproduce on `main` at `f81626d`: slice 3e's `stage3_versions` already holds the
grading's `[repeats]` (`min_allele_reads` and every `[repeat_loci]` row but its wording fields
`note`, `topic`, `evidence` and `validity`) and `[exclusion]`, each as JSON, so `open_stage3`
refuses a table measured under another `normal_max`.
`tests/test_calibrate_stage3.py::test_versions_follow_the_grading` covers it and passes on
`main`. The rest was not added: `measure` reads neither `[smn] min_parascopy_qual` nor
`[yleaf] min_qc_score` (it compares both SMN callers' raw copy numbers and Yleaf's L816 and
haplogroup), and the HG002 alignment's bwa version would be a record no decision reads.
