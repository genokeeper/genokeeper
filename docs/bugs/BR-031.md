- **Found:** 2026-11-06 (`genokeeper calibrate --only cnv` on HG002, the first build of the
  `cnv` table)
- **Where:** `src/genokeeper/cnv/callers.py`, `run_delly_cnv`; `src/genokeeper/deletions/callers.py`,
  `delly_shards`, with the same `list(pool.map(...))` in `src/genokeeper/annotate/vep.py`
  (SpliceAI's shards) and `src/genokeeper/explain.py`, `explain`.

Two defects, seen in one run. `run_delly_cnv` sharded `delly cnv` per chromosome on the
reading of 3b's `delly sr`, but DELLY 2.7.0's `cnv` mode has no region to shard on: every
shard is a whole-genome run. And `delly_shards` promised that a failure is raised once the
running shards finish, while `list(pool.map(...))` yields in submission order and its workers
go on through the queue: a failure in a later shard stays hidden behind the earlier ones, and
every queued shard still starts. The user sees hours of containers, a kernel OOM kill in
Docker's VM, and no table.

**Evidence.** The 24 shards ran 14 at a time on a 46.96 GiB Docker VM, whose kernel OOM-killed
six; the `cnv` table was not built. The rest was measured on the public sample HG002 by the
calibration session, on the running containers and in DELLY's source at v2.7.0:

- `src/coral.h` reads `hasExcludeFile` only at line 478, on the finished `cnvs`, keeping an
  event when at least half its bases are in valid regions. Its `Count fragments` loop (line
  129) runs over every contig: `chrNoData` returns false for any path ending in `cram`
  (`src/util.h:651`), so it skips nothing here, and the loop skips only a contig absent from
  the FASTA. `src/scan.h`'s `Scanning Windows` does not read the exclude list. On this path
  the one other read of `hasExcludeFile` is `src/util.h:714`, inside the parser that
  `coral.h:482` calls.
- The chrX and chrY shards started together. After an hour they had read 103.174 GB and
  103.178 GB, with VmHWM 4,898,320 and 4,898,424 kB. Each shard's peak so far is about
  4.67 GiB, whatever the chromosome. The two shards that never queued ran 4,104 s.
- After the first kill at about 00:24 CET, ten more shards started, the last at about
  01:40 CET.
- 3b's `delly sr` really does shard: its chr20 shard took 72 s against 54 min for a
  whole-genome run. `delly_shards` stays for it.

`tests/test_parallel.py::test_a_later_failure_stops_what_has_not_started` on today's shape,
with `map_until_failure` reduced to `list(pool.map(fn, items))`:

```
>       assert sorted(started) == [0, 1]
E       assert [0, 1, 2, 3, 4, 5] == [0, 1]
1 failed, 1 passed in 0.02s
```

**Suggested fix (a hypothesis):** one `delly cnv` container, its exclude list holding the
template, the masked intervals and a whole-contig line for every contig outside `shards`; a
helper over `concurrent.futures.wait` with `FIRST_EXCEPTION` for the pools. Must not change:
`delly sr`'s shards, and which calls `delly cnv` keeps. Considered: shard sizing by memory,
which would keep paying for 24 whole-genome runs, and killing the running containers, which
nothing here needs.

**What this evidence does not establish:** `delly sr`'s peak memory. `run_delly` passed at 14
shards on this VM, but that peak is unmeasured, so a smaller Docker VM may still overrun it;
settling that takes the peak measured per shard. Whether the single `delly cnv` run stays
near 4.67 GiB to its end is not measured either: that peak was read on running shards, and
the next run of `genokeeper calibrate --only cnv` shows it.

## Fix

`run_delly_cnv` runs one container behind `dna:cnv`. Its exclude list holds DELLY's template,
the masked intervals and every contig of the FASTA outside `shards`, so a female's calls stay
off chrY and every run's off the non-primary contigs. The `bcftools concat` and the `threads`
parameter are gone, as is `delly_shards`' `extra`, which only `delly cnv` used. By DELLY's
source its FILTER PASS records are the same ones, but their IDs now number across the run
instead of restarting per shard; only `read_delly_cnv` reads an ID, into the `callers` string.
`CNV_STEP_VERSION` is 2. The table has never been built and no `dellycnv` step is cached, so
nothing measured is lost.

`parallel.map_until_failure` replaces `list(pool.map(...))` in `delly_shards`, SpliceAI's
shards and `explain`. The suggested fix alone does not stop a queued item: the worker that
failed took the next item before the waiting thread woke, in 200 of 200 trials of a plain
`wait(FIRST_EXCEPTION)` with the queue cancelled after it. So each call first checks whether
one has failed. That stop is the pool's, not the container's: an item no worker has taken
never starts, but a worker already inside `fn`, waiting at the core gate, still starts its
container. SpliceAI's pool has as many workers as shards, so nothing queues in the pool and the
helper changes only which failure is raised.

Covered by `tests/test_parallel.py::test_a_later_failure_stops_what_has_not_started` (it fails
on `list(pool.map(...))`, and on a plain `wait` with `assert [0, 1, 2] == [0, 1]`),
`tests/test_deletion_callers.py::test_run_delly_shard_fails_the_step`,
`tests/test_cnv_callers.py::test_run_delly_cnv_args` (with and without chrY in `shards`) and
`tests/test_pipeline_invariants.py::test_female_no_haploid`. No real `delly` run went with this
fix.

Deliberately not changed: `delly sr`'s shards and their count, because no memory-based sizing
goes in until its peak is measured; running containers, which are neither killed nor retried
after a failure; the gate, with no second check after it, because only `delly sr` still queues
and its shards are short.

Partial, not fixed: `delly cnv`'s whole-genome shards and the hidden failure are gone, but
`delly sr` keeps a fan-out sized by CPU count and an unmeasured peak, so a smaller Docker VM
stays open.
