- **Found:** 2026-11-10, by reading the code at `d2f9e48` (no run reproduced it)
- **Where:**
  - `src/genokeeper/calibrate/build.py`, the small-variant builder: `if record is not None and record.gvcf is not None: pair = None  # scored from its record`, then `gvcf = read_called(lab, "hg003")`;
  - `small_variants_versions` (`calibration_versions(lab, tools=genome_tool_versions(), …)`);
  - `src/genokeeper/calibrate/records.py`, `Record` and `read_called`.

The table is stale when any of the pipeline's seven `VERSION_KEYS` (`calibrate/table.py`)
differs from what it was measured with: `deepvariant_image`, `checkpoint_md5` and
`make_examples_flags` among them. `genokeeper calibrate` then rebuilds it. When HG003's record
already holds a gVCF, the builder scores that gVCF as it is, without calling HG003 again. It
then writes the table under `genome_tool_versions()`, the current pipeline's.

The record keeps the CRAM's align key and the gVCF's path. It keeps nothing of the caller that
wrote the gVCF, and `read_called` checks only that the file exists and the reference matches. So
after a DeepVariant image, checkpoint or flags change, the table reads current for the new
caller while its error rates were measured on the old caller's calls. Every run would then
grade small variants with those rates and no warning.

A second instance, found by a review of the README's first workaround: the call step's own
cache key (`call_step` in `pipeline.py`: `CALL_STEP_VERSION`, the alignment key, the
DeepVariant image, the FASTA, the checkpoint, the sex and `[par]`) does not hold
`CALLING_FLAGS` (`call/deepvariant.py`). So after a flags-only change every run, the owner's
included, reuses the old calls, while `calibration_versions` records the new flags. A
documented manual workaround (move the records aside, align and calibrate again) was dropped:
it reused the cached calls on a flags change, and on a library whose reads came from a
`realign` it refused (`check_platform` reads ENA's accession) after the record was moved,
leaving the lab without a record.

Evidence: the code paths above, read at `d2f9e48`. `hg002_cells_versions` has the same shape: its
`pcrfree` key is HG002's align key, not its calls'.

**Suggested fix (a hypothesis):** record the caller's versions with the gVCF when
`run_sample` writes it (the three caller keys of `VERSION_KEYS`). Then `read_called`, or the
builder, calls the sample again when they differ from `genome_tool_versions()`. The same applies to
HG002 PCR-free's gVCF behind `hg002_cells`. Must not change: a table whose caller did not
change still reuses the gVCF, which saves hours. Alternative considered: put the gVCF's own
sha256 in the table's versions, but that cannot tell which caller wrote it.

**What this evidence does not establish:** that any table on a real lab is affected today: whether a
caller version changed between a gVCF's calling and a later rebuild was not checked. Settling
it would take a test that changes
`deepvariant_image` in the record's world and asserts the builder calls again, plus a check of
which other builders reuse a recorded gVCF the same way.
